# 链 3 · LRC 兜底切分修复（对应提交 `14e9153`）

- **日期/工具**：2026-10-24 晚 · ZCode CLI（GLM 大模型驱动的编码 Agent）

## 1. 背景与目标

「K-pop 学歌」功能支持上传 LRC 歌词文件，AI 自动识别歌名/歌手并生成带罗马音、翻译、语法点的歌词卡。当天傍晚我刚让 AI 测完整个文件上传链路并修复了几个问题（视觉提取防幻觉、曲库劫持等，提交 `4eccf2a`），想**亲眼在网页上走一遍成功案例**——这一走，暴露了一个更小的 bug。

## 2. 我的 Prompt 原文

**第 1 轮（上游背景：让 AI 自测上传链路）：**

> 「你对ai的文件上传功能进行测试，如果有问题进行优化」

**第 2 轮（本条链的核心 Prompt：看真实成功案例）：**

> 「打开网站我看看lrc歌词上传的成功案例」

## 3. AI 的方案与关键决策

AI 打开网页，在应用内浏览器里注入了一个带元数据的演示 LRC 文件（`[ti:봄날][ar:BTS]` + 3 句带时间轴的歌词），完整走了「上传 → AI 分析 → 确认歌名 → 保存 → 学习页」流程。第一次分析撞上了免费档晚间限流，系统按设计**降级为兜底行切分**——歌词卡只显示原文并提示「信息不完整」。

等限流恢复的间隙，AI 在兜底产物里发现了一个小 bug：**「歌名： 봄날」这行元数据被当成歌词切进了第一张卡**。定位：LRC 解析失败走兜底切分时，没有排除 `歌名:`/`歌手:`/`【LRC…】` 这类元数据行。修法极小：兜底切分前过滤元数据行（最终只改了 3 行）。

## 4. 问题与引导修复 ⭐（评分核心）

这条链最能说明「AI 协作的迭代粒度」：

- **Bug 是真实使用中暴露的，不是测试用例里假想的**：第 2 轮 Prompt 要的是「成功案例」，结果先等来一次限流降级——恰恰是这次降级，把平时很少走到的兜底路径推到了眼前
- **AI 在等待窗口自主发现并修复**，没有把时间耗在空转重试上；修复后跑测试、重启服务
- **防回归与重验**：删掉带脏数据的歌词卡，重新上传同一个 LRC 文件完整走一遍——这次 AI 真正分析成功，3 句干净歌词卡 + 语义总结，每句带罗马音、翻译、语法点、可收藏重点词

我的引导作用还是那句「打开网站我看看成功案例」：**验收走用户真实动线，而不是听 AI 汇报测试结果**。限流是意外，但坚持「眼见为实」让兜底路径里的 bug 无处可藏。
